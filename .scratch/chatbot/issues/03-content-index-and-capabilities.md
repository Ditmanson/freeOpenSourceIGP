# 03: Site content index and real capabilities (search + video links)

**What to build:** The chatbot becomes genuinely useful and grounded in real site content, gated behind the safety net from ticket 02. Adds a Hugo build-time content index, a single capability config file defining the chatbot's tools, and wires both into the Lambda along with prompt caching for the repeated context.

**Blocked by:** 01, 02 (the rate-limit/spend safety net must exist before the Lambda does anything more expensive or capable)

**Status:** done

- [x] Hugo generates a JSON content index at build time (a custom output format, the same mechanism used for client-side search widgets) containing at minimum each page's title, URL, tags, and a short summary/excerpt - kept current automatically as content changes, no manual maintenance
- [x] A single capability config file (bundled with the Lambda deployment) defines the chatbot's available tools as a list with at least a name, description, and enabled flag - at minimum `search_site_content` and `list_videos`, both enabled
- [x] The same config file also defines `send_email` and `check_calendar` entries, explicitly `enabled: false` - establishing the shape for later expansion without a handler-code redesign
- [x] The Lambda's handler logic reads this config file and only offers *enabled* tools to the model via Claude's tool-use mechanism - disabling a tool in the file is sufficient on its own to make the model unable to use it, with no other code changes required
- [x] The site-content-index context is sent using Bedrock/Claude's prompt caching mechanism (`cache_control: ephemeral` on the system prompt block), since it's identical across requests within its cache window
- [x] Verified via direct `curl` calls to the Function URL: "Do you have any posts about nosework or tracking training?" returned real posts (Griz 5 Months Tracking, Tracking 17 weeks, Detection 1, etc.) with real URLs; a video-recommendation question returned real video posts with URLs; an off-topic question ("What is the capital of France?") was correctly declined rather than answered from general knowledge
- [x] Verified that disabling a tool in the config file actually removes the model's ability to use it, not just aspirationally: temporarily set `list_videos.enabled` to `false`, redeployed, and re-asked the video question - the model fell back to `search_site_content` and explicitly hedged that it couldn't confirm video content, rather than calling the disabled tool. Re-enabled and redeployed the real config afterward.
- [x] `public/` changes (the generated `index.json` and its build machinery) were committed and pushed in this ticket, deviating from the original "no changes to public/" scope note - see Design notes below for why.

**Design notes:**

**Scope deviation, called out explicitly:** the original plan assumed the Lambda would receive site content passed in some other way, deferring any `public/` changes to ticket 06. In practice the simplest, most maintainable design was to have the Lambda fetch `https://griz.sh/index.json` live at runtime (cached per warm execution environment) rather than bundling a static copy at deploy time - this means content updates are reflected without redeploying the Lambda. That design requires the JSON index to actually be live at that URL now, not deferred to ticket 06, so `public/` was rebuilt and pushed this ticket instead. Recall from `docs/deploys.md`: AWS Amplify only publishes whatever's already in the committed `public/` directory, it does not run `hugo build` itself.

**Real bug found and fixed during verification, not just a happy-path pass:** the first live test returned an incomplete non-answer (`"Let me search more broadly for these topics:"`) instead of a real answer. Root cause: the tool-use loop was capped at `MAX_TOOL_ITERATIONS = 2` Bedrock calls, but the model sometimes wants to search a second time after seeing narrow first-pass results; when that happened, the loop exited after the 2nd call while the model's last response was itself another (unexecuted) tool-use request, and the fallback text-extraction returned whatever incidental preamble text preceded that tool call instead of a synthesized answer.

Fixed by restructuring the loop: `MAX_TOOL_ITERATIONS` raised to 3, and the *last* allowed call always omits the `tools` parameter entirely - the model literally cannot respond with `stop_reason: tool_use` on that call, so it's forced to synthesize a real text answer from whatever tool results are already in the conversation. This guarantees a bounded, predictable number of Bedrock calls per question (at most 3) while still tolerating a model that wants to search more than once. Also added a plain-language fallback string for the (now much rarer) case where the model still returns no text block at all, so the API never returns an empty string as an "answer". Re-verified live after the fix with the same test question - got a fully grounded, cited answer.

The reserved worst-case spend per request (`_MAX_REQUEST_COST_MICRODOLLARS`) already scales with `MAX_TOOL_ITERATIONS`, so raising it from 2 to 3 automatically widened the reservation - no separate change needed there.

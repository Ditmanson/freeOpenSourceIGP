# 04: CloudWatch alarm and notification for limit-hit events

**What to build:** The site owner is notified when the chatbot rejects a request for hitting a rate limit or the spend ceiling, using the same alarm/notification path already relied on for the AppSync alarms - not a new, separate notification mechanism.

**Blocked by:** 02 (only needs the rate-limit/circuit-breaker logic to exist, not the fuller capabilities from ticket 03)

**Status:** done

- [x] The Lambda publishes a custom CloudWatch metric when it rejects a request for a rate-limit or spend-ceiling reason - two distinct metric names (`RateLimitRejection`, `SpendCeilingRejection`) under a new `GrizChatbot` namespace, published via `_record_limit_metric`, which swallows publish failures so they never break the actual rejection response (the call is synchronous, not truly fire-and-forget - a slow `put_metric_data` call could add latency, but can't cause the rejection response to fail)
- [x] A CloudWatch alarm on that metric is wired to the existing SNS topic (`grizsh`) already used for the AppSync 4xx/5xx/latency alarms - two alarms created (`chatbot rate limit rejection grizsh`, `chatbot spend ceiling rejection grizsh`), both with `AlarmActions` pointing at the same `arn:aws:sns:us-east-2:861079997941:grizsh` topic, no new notification channel introduced. Period/statistic/treat-missing-data match the existing AppSync alarms' convention (300s period, Sum statistic, `missing`); threshold is 0 (alarms on any occurrence at all, rather than a volume threshold like the 4xx alarm's 50) since for a low-traffic hobby site a single limit-hit is itself the signal worth knowing about
- [x] Every mutating AWS command (the `PublishLimitMetrics` IAM inline policy - scoped via a `cloudwatch:namespace` condition to the `GrizChatbot` namespace only, not a blanket `PutMetricData` grant - and both `put-metric-alarm` calls) was surfaced to the site owner and explicitly confirmed before running
- [x] Verified by deliberately triggering rate-limit rejections (same approach as ticket 02: rapid requests from the same IP past `MAX_REQUESTS_PER_IP_PER_HOUR`) and confirming the full chain actually fired, not just that the alarm exists unconfigured: `get-metric-statistics` showed the real `Sum` datapoint, and polling `describe-alarms` caught the live `INSUFFICIENT_DATA` → `ALARM` transition with the reason text quoting the actual datapoint value that crossed the threshold
- [x] No changes to `public/`

**Design notes:** the first verification attempt technically published a real datapoint but ~25 minutes of wall-clock time elapsed before polling for the alarm transition (other work ran in between) - by the time of polling, the datapoint had scrolled out of the alarm's 5-minute evaluation window, so it correctly showed `INSUFFICIENT_DATA` rather than `ALARM`. Re-triggered rejections and polled promptly afterward to get a genuine live transition rather than assuming the first (inconclusive) result was good enough.

**Code review caught two real issues, fixed before shipping:**
1. The helper was originally named `_publish_limit_metric` and documented as "fire-and-forget," but the `cloudwatch.put_metric_data` call is actually synchronous - only the *failure* case is swallowed, not the latency. Renamed to `_record_limit_metric` with accurate wording, since the old name/docstring implied a guarantee (never adds latency) the code didn't actually provide.
2. The new `cloudwatch` client had no explicit timeout, inheriting botocore's ~60s default - since this client is only ever called from the fast-fail rejection path, a slow or throttled CloudWatch call could have stalled a 429 response for up to a minute. Fixed with an explicit short `Config(connect_timeout=2, read_timeout=2, retries={"max_attempts": 1})` scoped to just this client.

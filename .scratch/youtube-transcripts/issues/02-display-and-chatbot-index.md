**What to build:** A real visitor sees a "Youtube Transcripts" section at the bottom of any page with an embedded video, and the chatbot's grounding data includes transcript text so it can answer questions about what's actually said in a video.

**Implementation notes:**

- Hugo doesn't expose shortcode arguments directly, so video-ID extraction uses `.RawContent` + `findRE` + `substr` (Hugo's `findRE` returns full regex matches, not capture groups - since the ID is always exactly 11 characters, the last 11 characters of each match is the ID). This logic lives once in a new shared helper partial, `layouts/_partials/videoIds.html`, using Hugo's `{{ return }}` partial feature, called from both `youtubeTranscripts.html` (display) and `index.json.json` (chatbot index) so the two don't duplicate/drift from the extraction regex.
- Used `hugo.Data` instead of `.Site.Data` for data-file lookups - `.Site.Data` triggered a new deprecation warning (`.Site.Data was deprecated in Hugo v0.156.0`) that a first draft introduced; caught before committing and fixed in both files.
- **Deliberate constraint, not an oversight:** `index.json.json`'s `summary` field keeps its existing 400-character truncation length even with transcript text now folded in (prose and transcript share the same budget rather than growing it). The chatbot Lambda's spend-reservation math (ticket 03) sizes its worst-case cost estimate against this field's *current* length - silently growing it would understate real worst-case tool-result size without any corresponding Lambda-side change, and "no AWS/Lambda-side changes" is this ticket's explicit scope. Long-prose pages get correspondingly less transcript coverage in the index as a result; this trades some search recall for a guarantee that per-request cost doesn't quietly increase outside of a ticket scoped to review that math.

**Code review caught two real bugs, fixed before shipping:**
1. **False-positive transcript section.** `content/dogs/Griz-5-months-tracking.md` contains a malformed shortcode (`{{ <youtube 0qHwF1halxQ> }}`, a stray space after `{{`) that Hugo's real shortcode parser doesn't recognize as a real invocation - `.HasShortcode "youtube"` is `false` for that page, and no video actually renders for a visitor. The original `videoIds.html` regex was loose enough to match this malformed near-shortcode anyway (made looser still by an earlier same-ticket fix chasing regex parity with the fetch script), producing a spurious "Youtube Transcripts" section - and polluting the chatbot's search index - for a video that isn't actually embedded. Fixed by gating the whole extraction on `.HasShortcode "youtube"` first: Hugo's own shortcode parser is the ground truth for "is a video really here," not a hand-written regex trying to fully replicate its parsing rules. Verified live: the malformed-shortcode page now correctly renders nothing, while the real 6-video page is unaffected.
2. **HTML-entity corruption in the chatbot's search index.** Hugo's `truncate` function HTML-escapes its output (`'` → `&#39;`, `>` → `&gt;`), and this was always true even before this ticket - it stayed invisible because Hugo's typography renders prose with smart quotes (’, a different character from a literal `'`) which aren't in the escape set. Raw transcript text uses plain ASCII apostrophes and literal `>>` speaker markers, which *are* affected, so every transcript-bearing page's index entry contained visible `&#39;`/`&gt;&gt;` artifacts instead of real punctuation. Fixed by adding a second `htmlUnescape` after `truncate` (the existing one only ran before it, unescaping `.Plain`'s own entities, not truncate's newly-introduced ones). Verified: index entries for transcript-bearing pages now show clean `we're`/`that's`/`>>` instead of escaped entities.

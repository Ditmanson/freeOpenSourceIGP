# Restructure site content into dogs / meetups / tech / misc

## Problem Statement

This Hugo site (`griz.sh`) was originally organized around dog-sport disciplines the owner was tracking one at a time: `BH`, `IGP`, `Obedience`, `Nosework`, `Protection`, plus `Schedule` and `Misc`. The site's actual current use has outgrown that shape — content no longer maps cleanly to those folders (e.g. a Kubernetes setup guide currently lives under `Misc`), and the owner wants a structure that reflects how the site is actually used going forward: dog training content, meetup/schedule content, tech writing, and everything else.

## Solution

Reorganize `content/` into four top-level sections — `dogs`, `meetups`, `tech`, `misc` — plus the existing `tags` taxonomy, and update `hugo.yaml`'s menu to match. All dog-sport disciplines (BH, IGP, Obedience, Nosework, Protection) collapse into a single flat `content/dogs/` section, distinguished by tags rather than subfolders. `content/Schedule/` becomes `content/meetups/`. The one tech post (`k3s-setup.md`) moves out of `Misc` into a new `content/tech/`. Everything else in `Misc` stays in `content/misc/`.

`public/` (the built site, which is git-tracked in this repo) is never touched by hand — it's regenerated by the normal Hugo build/deploy step, not by this work.

## User Stories

1. As the site owner, I want all dog-sport training posts (BH, IGP, Obedience, Nosework, Protection) under one `content/dogs/` section, so that I don't have to keep inventing a new top-level folder every time I try a new discipline.
2. As the site owner, I want each dogs post tagged with its discipline (bh, igp, obedience, nosework, protection), so that I can still browse "all obedience posts" via `/tags/obedience/` even though there's no longer a dedicated folder or menu item for it.
3. As the site owner, I want each dogs post to keep its existing tags (dog names like `Griz`/`Argos`, topics like `Tracking`/`Barking`), so that no existing categorization is lost in the move.
4. As the site owner, I want my training-schedule/meetup posts under `content/meetups/` instead of `content/Schedule/`, so that the section name matches what the content actually is.
5. As the site owner, I want `k3s-setup.md` moved out of `Misc` into a new `content/tech/` section, so that tech writing has its own home separate from personal/dog-adjacent notes.
6. As the site owner, I want the remaining `Misc` posts (`chill.md`, `diet.md`, `small_challegnes.md`) to stay together as `content/misc/`, so that general non-dog, non-tech notes still have a catch-all home.
7. As the site owner, I want `hugo.yaml`'s main menu updated to show `Dogs`, `Meetups`, `Tech`, `Misc`, `Tags` (dropping the old `BH`/`IGP`/`Obedience`/`Nosework`/`Protection`/`Schedule` entries), so that site navigation matches the new content structure.
8. As the site owner, I want the homepage (`content/_index.md`) left in place at the root, so that the site's landing page is unaffected by the reorg.
9. As the site owner, I want old URLs like `/bh`, `/obedience`, `/protection`, `/schedule` to simply stop existing (no redirects/aliases), so that no extra complexity is introduced for a personal site with no inbound links to preserve.
10. As the site owner, I want the reorganized site to build cleanly with `hugo` and render the new section pages correctly, so that I know the restructure didn't break the site before it's deployed.
11. As the site owner, I want `public/` left completely untouched by this work, so that the build output isn't hand-edited or left inconsistent with the new source structure.

## Implementation Decisions

- **New content layout:**
  - `content/dogs/` — flat, no subfolders. All posts currently under `content/BH/`, `content/IGP/`, `content/Obedience/`, `content/Nosework/`, `content/Protection/` move here directly (filenames preserved).
  - `content/meetups/` — replaces `content/Schedule/`. All files move over as-is (filenames preserved).
  - `content/tech/` — new section containing only `content/Misc/k3s-setup.md`.
  - `content/misc/` — renamed from `content/Misc/` (lowercase to match the others), retaining `chill.md`, `diet.md`, `small_challegnes.md`.
  - `content/_index.md` stays at the root, unchanged.
- **Section index pages:** each new section (`dogs`, `meetups`, `tech`, `misc`) gets a minimal `_index.md` with just a `title` (and `date` where Hugo needs one), following the pattern of the existing `content/BH/_index.md`. The `BH/_index.md` currently embeds a heel-map image (`/bh_heel_map.png`) — that image reference is preserved by carrying it into `content/dogs/_index.md` (or into the BH post it's most relevant to; agent's judgment during implementation, but must not be silently dropped).
- **Tagging on migration:** every post moving into `content/dogs/` gets one discipline tag added to its existing `tags:` front matter, based on which old folder it came from:
  - `content/BH/*` → tag `bh`
  - `content/IGP/*` → tag `igp`
  - `content/Obedience/*` → tag `obedience`
  - `content/Nosework/*` → tag `nosework`
  - `content/Protection/*` → tag `protection`
  Posts without an existing `tags:` field get one added with just the discipline tag. Posts with existing tags get the discipline tag appended, preserving current tags (e.g. `Griz`, `Argos`, `Tracking`, `Barking`, `Shaping`, `Chill`, `petdogskills`).
  - `content/meetups/`, `content/tech/`, `content/misc/` posts are **not** auto-tagged by this work — no discipline concept applies there.
- **`hugo.yaml` menu:** replace the six discipline/schedule menu entries (`BH`, `IGP`, `Obedience`, `Nosework`, `Protection`, `Schedule`) with four entries — `Dogs` (`/dogs`), `Meetups` (`/meetups`), `Tech` (`/tech`), `Misc` (`/misc`) — keeping `Tags` (`/tags/`) as-is. Preserve ascending `weight` ordering; exact weight values are the agent's judgment as long as ordering is `Dogs, Meetups, Tech, Misc, Tags`.
- **Taxonomies:** `taxonomies: tag: "tags"` in `hugo.yaml` is unchanged.
- **No redirects/aliases:** old URLs (`/bh`, `/igp`, `/obedience`, `/nosework`, `/protection`, `/schedule`) are allowed to 404. No `aliases:` front matter is added.
- **`public/`:** not modified by this work under any circumstances. It is git-tracked but is build output regenerated by a separate deploy step, out of scope here.
- **`layouts/`:** no template changes are anticipated (section/list/taxonomy templates are already generic — `layouts/section.html`, `layouts/taxonomy.html`, `layouts/term.html`), but if the new section names surface a template gap during the build-seam check, fixing it is in scope.

## Testing Decisions

- No traditional test suite exists for this Hugo site (no application code, no test framework configured).
- The verification seam is the **Hugo build**: run `hugo` (or `hugo --gc --minify`, matching whatever the deploy step uses) against the new `content/` + `hugo.yaml` and confirm:
  - The build completes with no errors/warnings about missing templates or broken shortcodes.
  - Section pages exist and are reachable: `/dogs/`, `/meetups/`, `/tech/`, `/misc/`, `/tags/`.
  - A sample of migrated posts render at their new URLs with their original content and (for dogs posts) both old and new tags present.
  - `public/` diff (if inspected) is understood to be build-output churn only, not hand-edited.
- No automated test file is expected to be added as part of this work; this is a content/config restructure, not application logic.

## Out of Scope

- Any changes to `public/` (build output).
- Any styling/theme/layout redesign beyond what's needed to keep the four new sections rendering (no new visual design work).
- Adding redirects or `aliases:` for old URLs.
- Changing `content/_index.md` (homepage) content.
- Renaming or retagging posts already in `content/Misc/` other than moving `k3s-setup.md` to `tech`.
- Any deploy/CI pipeline changes.

## Further Notes

- Filenames are preserved during moves (e.g. `content/BH/dan_argo_bh1.md` → `content/dogs/dan_argo_bh1.md`) unless a collision occurs across merged folders, in which case the agent should flag the collision rather than silently overwriting.
- `content/IGP/IGP_rules.md` is a reference page (ruleset link + scoring notes), not a training log entry, but per the "flat + tags" decision it still moves into `content/dogs/` tagged `igp` like everything else — no special-casing.
